# 从零设计一个 Coding Agent：小白版方案与流程

设计日期：2026-11-01。本文是待实施的方案，不代表产品已开发或效果已经验证。

## 1. 先明确你要做成什么

这里把“这样的 coding agent”理解为：你用自然语言描述一个编程任务，它能读取选定的项目、修改代码、运行检查，最后交付可查看、可撤销的改动。目标是做出类似的核心体验；本文不声称掌握当前应用的内部实现。

第一版定位：Windows 本地、单人使用、一次处理一个小任务；调用现成的云端模型，自己实现执行流程。先有命令行版本，再增加本地浏览器界面。选择文件、搜索、检查配置先围绕小型 JavaScript / TypeScript 项目设计。

第一版只追求这个结果：

> 我说“修复购物车空列表计算错误”，它能找到相关文件，做出修改，运行已有检查，并让我查看修改前后的差异。

把登录、付费、团队协作、手机端、多 Agent、插件市场、远程服务器和复杂代码索引放到后续版本。先完成一条从需求到可验证改动的流程。

## 2. 它是怎么工作的

可以把产品理解成五个部分：

- **大模型是顾问。** 理解你的需求，分析代码，提出下一步动作。通过 API 使用已有模型，起步阶段无需训练自己的模型。
- **工具是手。** 读取文件、搜索文本、应用修改、运行检查都由程序完成。
- **Agent 运行程序是调度员。** 把需求发给模型，识别工具请求，校验并执行工具，再把结果发回模型，控制整个循环。
- **项目工作区是工作台。** 存放这次任务可以读取、修改和运行的项目副本。
- **界面是观察窗口。** 显示需求、进度、实际工具记录、代码差异和检查结果。

例如，模型输出“请读取 cart.ts 的第 1–100 行”，并不意味着它已经读到了文件。你的程序必须收到请求、读取文件并返回内容，模型才能继续分析。

这就是工具调用：模型请求动作，应用执行动作，把结果返回给模型。官方文档给出了对应的多轮流程，见 [OpenAI Docs：Function calling](https://developers.openai.com/api/docs/guides/function-calling)。

## 3. 先认识这些词

- **前端**：用户看见并点击的界面。
- **后端**：接收请求、保存数据、调用模型和工具的程序。本方案中运行在你的电脑上。
- **API**：两个程序沟通的接口。你的程序通过它向模型提交请求。
- **API Key**：调用服务的凭据，由后端保存，不能出现在网页代码、聊天记录或测试项目中。
- **CLI**：在终端里使用的命令行程序，适合先验证核心逻辑。
- **工具调用**：模型按照规定格式请求一个动作，例如读取文件。
- **上下文**：这次提供给模型的任务、相关代码、历史操作和检查结果。
- **Diff**：修改前后的差异，告诉你哪些行被增加或删除。
- **Git**：记录代码版本的工具，可以用来比较和恢复改动。
- **沙箱**：限制代码运行范围的独立环境，减少测试项目对电脑其他部分的影响。
- **测试**：自动检查程序行为是否符合预期的代码。
- **MVP**：最小可用版本，能完成最重要的一条用户流程。

不需要一开始学完所有术语。开发到哪个阶段，就学习对应的概念。

## 4. 用户操作流程与界面设计

首版用户流程：

1. 选择一个练习项目，说明这次允许修改的范围。
2. 输入任务和完成标准，例如“空购物车总价应为 0，原有测试仍应通过”。
3. 查看 Agent 正在搜索、读取、修改或检查什么。
4. 遇到需要额外授权的操作时，查看具体命令和影响范围再决定。
5. 查看代码差异与检查结果，接受或丢弃本次修改。

本地浏览器界面建议分成三块：

- 左侧：项目、任务列表。
- 中间：对话、简短计划、真实工具执行记录和停止按钮。
- 右侧：变更文件、代码差异、检查结果、接受与丢弃按钮。

首版页面可以只有聊天区和差异区，屏幕较小时分标签显示。显示“正在读取某文件”和真实命令日志即可，不需要展示模型的隐藏推理过程。

任务状态至少区分：准备中、执行中、等待用户、待审阅、失败、已取消、预算耗尽。模型生成一句“完成了”，不能直接让界面显示“验证通过”。

## 5. 软件内部如何连接

```text
用户：修复一个错误
        ↓
命令行 / 本地网页
        ↓
本地后端 + Agent 运行程序
        ├── 模型 API：判断下一步做什么
        ├── 上下文管理：挑选相关代码和结果
        ├── 工具层：校验参数、范围和权限
        │      ├── 文件列表 / 搜索 / 按行读取
        │      ├── 应用修改 / 查看差异
        │      └── 在隔离环境中运行检查
        └── 记录：任务状态、工具结果、用量
                      ↓
               结果返回模型，继续下一轮
                      ↓
               代码差异 + 检查证据 → 用户审阅
```

最重要的职责划分：模型建议做什么，程序决定是否允许以及如何执行。读取、写入和命令执行都要经过工具层；不能用一段提示词代替实际访问控制。

### 推荐的学习路线与另一种实现方式

本方案选择“自己实现一个简单循环 + Responses API”，方便理解每一层，也方便连接本地项目。

当前官方同时提供托管的 Agents API 和运行在应用内的 Agents SDK。托管方案可以减少部分编排工作；它仍需要产品界面、项目接入、权限和审阅设计。它与自建循环是可选择的路线，无需同时学习三套。参见 [OpenAI Docs：Agents](https://developers.openai.com/api/docs/guides/agents)。

## 6. 技术选型：先保持简单

下面是本方案的建议，并非唯一答案。依赖版本在真正开发时再核对、锁定。

- **JavaScript 入门，逐步使用 TypeScript**：前后端共用一门语言。TypeScript 可以帮助检查函数输入输出是否写错。
- **Node.js**：让 JavaScript 在浏览器外运行，用于读取文件、启动后端和调用 API。
- **模型接入：官方 SDK + Responses API**：只接一个服务商，模型名称放在配置里，根据账户实际可用性选择支持工具调用的模型。
- **界面：React + Vite**：等命令行闭环完成后再引入，用来做聊天区、任务状态和差异审阅。
- **存储：早期 JSON 记录，之后 SQLite**：早期只保存开发用任务记录；增加重启恢复和多个会话时再引入数据库。
- **代码管理：Git**：记录原始版本、比较差异。早期先用项目副本，熟悉之后再使用独立工作树等能力。
- **代码定位：文件名和文本搜索**：先做到找到并读取相关代码，再依据实际问题决定是否需要复杂检索。
- **命令执行：受限制的隔离环境**：在接通自动运行测试之前引入；不把任意模型输出直接交给宿主终端。

起步时不需要 GPU、模型训练、向量数据库或分布式集群。模型在云端完成推理，本机负责应用和工具。若以后要求代码完全不出本机，则需要另行设计本地模型路线并评估硬件与效果。

## 7. 设计流程：先定义结果，再分阶段实现

开发前写一页需求说明即可，回答四件事：谁使用、解决什么任务、允许改哪里、怎样判定完成。

先画用户流程，再画上面的模块连接图，接着定义工具的输入输出。之后每次只实现一个能亲眼验证的新能力。以下阶段是先后顺序，不是已经完成的进度。

### 阶段 0：建立最少的基础

学习：文件与路径、变量、函数、数组、对象、JSON、异步请求，以及终端和 Git 的基本操作。

动手：写一个脚本，读取练习目录里的文本并打印；制造一次错误，看懂错误信息；手工修改文件并查看差异。

验收：能启动脚本、知道文件来自哪里、知道失败发生在哪一行，并能恢复练习改动。

### 阶段 1：做一个会聊天的命令行程序

动手：终端输入需求，后端调用模型，终端显示回答；处理密钥缺失、网络失败和用户取消。

验收：能连续进行两轮对话，报错时能看清原因，密钥没有出现在输出中。

学到：API、消息历史、异步请求。这个阶段让模型分析手工提供的文本即可。

### 阶段 2：让它读取项目

动手：实现 list_files、read_file、search_text 三个工具。先手工调用验证，再注册给模型使用。默认跳过依赖目录、二进制和敏感文件。

验收：问“购物车总价在哪里计算”，它能通过真实搜索指出文件、函数和行号；超出练习目录的读取被拒绝。

学到：工具参数、调用结果、上下文。读取结果带行号和截断标记，不把整个项目一次发给模型。

### 阶段 3：让它做可撤销修改

动手：创建独立的任务副本，实现 apply_patch 和 inspect_diff。补丁就是只描述需要修改的部分；应用前确认文件内容仍与读取时一致。

验收：能修复一个小错误，展示新增、删除和修改内容，丢弃任务后原项目保持原样。原文件发生变化时提示冲突，不静默覆盖。

学到：版本基线、代码差异、冲突。接受修改是用户操作，模型不能代替用户接受。

### 阶段 4：让它运行检查

动手：先为练习项目配置固定检查命令，例如测试和类型检查；在隔离环境中执行，收集标准输出、错误输出、退出码和耗时。设置超时，并能停止整个任务的执行进程。

验收：正确识别通过、失败、超时和取消；无法运行的检查显示“未验证”。此时限制工具为预配置命令，暂不开放通用 shell。

学到：进程、执行环境、退出码。固定命令仍可能运行项目里的代码，因此项目副本与命令白名单都不能代替隔离环境。

### 阶段 5：接成自主处理任务的循环

动手：把“模型请求 → 校验 → 执行 → 结果回传”循环起来。检查失败时回传真实日志，让模型尝试修复。设置模型请求次数、总耗时和费用预算。

验收：输入一次“小错误修复”任务，能完成定位、修改、检查和差异交付；达不到目标时说明失败原因并保存已有结果。

学到：Agent 循环、任务状态、停止条件。先让单个 Agent 稳定完成小任务。

### 阶段 6：增加本地聊天界面

动手：网页显示对话、实际工具事件、停止按钮、代码差异和检查结果；通过后端执行全部操作。

验收：用户能够看懂当前在做什么，停止运行，审阅并接受或丢弃修改；刷新页面不会再次执行同一条命令。

学到：前后端接口、流式进度、事件记录。网页不保存模型密钥，也不能直接获得系统命令权限。

### 阶段 7：让它可持续使用

动手：用 SQLite 保存任务和工具状态；加入断网处理、重启核查、日志脱敏、任务用量统计和安装说明。

验收：关掉程序后能查看历史；中断后先核对文件和进程状态，不盲目重复执行写入；新安装环境能走通一次真实小任务。

学到：持久化、恢复、发布。早期 JSON 记录不承诺可靠恢复，这一阶段再补全恢复语义。

零基础的进度更适合按这些验收点衡量。若每天投入 1–2 小时，可先以数月的学习与迭代作为预期，再按前两阶段的实际速度调整；这不是交付工期承诺。

## 8. 一次任务的具体例子

需求：修复购物车为空时总价计算错误，保持已有功能。

1. 程序固定这次任务的原始代码版本。
2. 模型请求搜索“total”及购物车相关文件。
3. 工具返回候选文件和行号，模型请求读取相关代码与已有测试。
4. 模型提出补丁，程序检查范围和内容后应用到任务副本。
5. 程序运行固定测试，保存实际退出码和日志。
6. 如果失败，把失败信息送回模型；它在剩余预算内调整修改。
7. 检查完成或达到限制后，展示差异、检查结果和未解决事项。
8. 用户审阅后选择是否接受修改。

“测试全部通过”只能说明已运行的这些检查通过，不代表所有可能的情况都正确。新功能仍要结合任务的完成标准进行验收。

## 9. 工具设计到什么程度就够了

每个工具先写三句话：它做什么、输入什么、返回什么。

- list_files：列出允许目录内的文件，支持数量上限。
- read_file：输入相对路径和行范围，返回内容、行号、当前文件版本标记。
- search_text：输入关键词和范围，返回路径、行号、匹配片段。
- apply_patch：输入预期文件版本和局部修改，返回受影响文件或具体冲突。
- run_check：输入已配置的检查名称，返回日志、退出码和执行状态。
- inspect_diff：返回本次任务相对于基线的完整差异。

所有工具统一返回成功与否、数据、错误原因和输出是否截断。长日志保存在本地，模型需要时分段读取。前端“接受修改”不作为模型工具开放。

## 10. 核心循环的概念示意

以下只是解释逻辑的伪代码，不能直接运行：

```text
建立任务与代码基线
重复，直到完成、取消或预算耗尽：
    收集任务目标、相关代码、最近差异、最新检查结果
    请求模型，保存能够继续会话的完整响应项
    如果有工具调用：
        验证工具名称、参数、路径与授权
        执行工具并记录真实结果
        把结果与原调用 ID 配对后回传
    否则：
        判断是否有交付物，要求的检查是否已经执行
        满足条件则进入待审阅；否则继续或明确说明无法完成
展示代码差异、验证证据和未完成事项
```

应用应记录可验证的动作与结果，不能依赖模型的口头描述判断工具是否执行。恢复会话也要保留协议需要的响应项，不能只保存用户看见的聊天文本。

## 11. 从首版开始保留的工程约束

- 任务文件访问被限制在明确范围内；按真实路径检查，处理路径穿越、符号链接和 Windows junction。
- API Key 留在本地后端；敏感文件不进入模型上下文或测试环境。云端模型会收到你实际发送的代码片段。
- 执行项目代码时使用隔离环境，并限制网络、资源和运行时间。项目副本和 Git 工作树只用于管理修改。
- 仓库说明和工具输出都是待分析内容，不能改变程序规定的权限。
- 用户可随时取消；只撤销 Agent 本次改动，不能覆盖用户后来进行的编辑。
- 达到模型请求次数、时间或费用上限后停止并报告已有结果。这里的预算上限是你设计的产品配置。

这些约束分阶段落地：只读阶段做访问限制，修改阶段做基线和撤销，执行阶段做隔离与取消。官方也强调文件、网络和执行权限的边界，参见 [OpenAI Docs：Sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security)。

## 12. 如何知道做得好不好

准备五类固定练习任务：解释一个函数、定位错误、修复小错误、补一个测试、增加小功能。每个任务写好原始版本、需求与独立检查方法。

同一批任务重复运行，记录完成情况、检查结果、无关改动、人工介入、用时和模型用量。检查代码和验收数据放在 Agent 不能修改的地方，防止“把检查改简单了”被误判为成功。

还要专门试四种异常：API 失败、路径越界、文件冲突、执行超时。真实数据出现后，再决定优先优化模型、上下文还是工具。

## 13. 成本与第一天的行动

开发成本主要来自模型调用、学习时间，以及后续可能使用的执行环境。模型会在一个任务中被调用多次，不能按“一条用户消息等于一次调用”估算。

费用估算按实际服务的输入、缓存输入、输出及工具/执行环境计费规则计算，不在此固定价格。起步记录每个任务的用量，设置本产品自己的预算上限；账户权限、配额和结算以实际服务后台为准。

第一天只完成三件事：

1. 学会在编辑器中创建一个脚本，并从终端运行它。
2. 准备一个独立练习目录，放入几个能看懂的小文件。
3. 写一个脚本，只读取练习文件并打印结果，再故意输入不存在的路径观察报错。

完成后再进入 API 对话阶段。每次让 AI 协助开发时，可以这样提出任务：

> 我在做一个本地 coding agent，现在只做“读取练习文件”阶段。请先解释要创建哪些文件，再分小步实现；每一步说明输入、输出、运行方法和验收结果。暂时不要增加聊天界面和其他功能。

建议先读本文并按阶段实施。工程化细节可参考工作区已有的 [技术方案](coding-agent-technical-plan.md)，实际实现时再逐项展开。
