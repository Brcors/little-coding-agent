# 语义理解到 Function Calling · v0.5

日期：2026-11-02。

## 小白可以这样理解

需求解析器负责整理“你想得到什么结果”，执行模型负责决定“接下来用哪个工具”。例如“没买任何东西时，金额应该是零”，不必由用户指出文件名：模型可以先列文件、搜索计价逻辑、读取实现，再决定修改哪些代码。工具函数本身由程序执行，模型不能自行执行 shell 或接受改动。

本例描述的是系统支持的流程，不代表当前已经用真实模型成功完成该自然语言任务。没有配置 API 凭据时，固定演示只能展示程序动作。

## 两阶段架构

```text
原始问题、澄清回答
  → 需求解析器：Responses API + Structured Outputs
  → Zod 校验 → 必要时继续澄清 → 用户审阅并确认
  → SemanticExecution：原始问题、目标、范围、验收标准、来源、版本
  → 权限交集：项目配置 ∩ 任务选项 ∩ 语义任务类型
  → 执行循环：Responses API + Function Calling
      1. 只提供读取/证据工具，tool_choice=required
      2. 校验并执行工具，把 function_call_output 按 call_id 返回
      3. 取得项目内容后，下一轮开放权限允许的其他工具
      4. 模型根据实际反馈继续选择工具，或给出结果
  → 自动补跑可用检查 → 差异、调用记录、报告 → 用户接受
```

这是串行分工架构，执行阶段是单 Agent 的 ReAct 风格工具循环。没有并行 Agent、训练、向量库或预先安排好的工具序列。

“任务类型 → 权限”由程序做确定性收紧；“目标与观察 → 工具名和参数”由执行 LLM 决策。解析阶段没有文件工具，不能验证代码；工具调用不是解析器输出一段函数名称后由页面直接执行。

## 交接和执行约束

`SemanticExecution` 保存在 `task.json` 的 `semantic` 字段中，记录解析 ID/版本、来源与模型、原始问题、目标、范围、约束、验收标准、澄清回答、假设、最终工具权限、证据调用 ID 和解析用量。`analysis.json` 保存原始解析快照。

用户材料与解析结果作为 JSON 放入 `user` 消息，系统指令独立提供。解析内容、项目文件和工具输出不能改变程序权限。解释和审查类型为 `read_only`，不能修改文件或运行项目代码；修复、新增等类型为 `workspace`，仍受项目 `.coding-agent.json` 的只读配置约束。

开始执行时只发送读取/证据工具的严格 schema，并设置 `tool_choice: required`。程序也会核对工具是否确实在本轮提供，拒绝模型伪造的其他调用。即使一次响应包含“先读取，再修改”，后一个操作也不会提前获得权限；模型必须在后续请求中看到读取结果。

成功的文件内容读取、文本匹配，或允许工作区根目录确实为空，可记录为内容证据。单纯列出非空文件清单、空搜索和读取失败不算。连续两次无内容证据就返回最终答案，任务标记失败。这个门槛只证明模型获得过内容，不保证读对了文件或准确理解了用户。

取得证据后改为 `tool_choice: auto`，模型可以选择继续搜索、读取、修改、运行预配置检查、查看差异，或结束。参数经过 Zod 再次校验，工具串行执行，结果与错误按调用 ID 回传。检查失败仍反馈模型迭代；禁用或无法运行检查时保持 `unverified`。

如果 API 拒绝、不完整响应、预算不足或用户取消，本轮不会被当作成功交付。API 拒绝与函数调用同时出现时，拒绝该轮所有工具。用户仍可审阅已保留的差异。

## 前端怎么使用

1. 在本地 `.env` 填好 `OPENAI_API_KEY` 和 `OPENAI_MODEL`，运行或重启 `npm run ui`。模型需支持 Structured Outputs 和 Function Calling。
2. 打开 [工作台](http://127.0.0.1:4317/)，选择真实项目，描述问题，点击“先解析需求”。
3. 确认解析方式为“LLM 解析”，审阅目标和范围，补充关键问题。
4. 在“理解后如何执行”中查看权限，点击“确认并执行”。
5. 在执行状态卡查看语义来源、项目内容证据与允许工具；活动流展示模型选择的工具，“工具记录”展示参数与结果。
6. 审阅差异和检查证据，决定是否接受。未接受前不会写回原项目。

“规则解析”只整理基础关键词；可以交给真实执行模型，但语义来源会保持 `rules`。“购物车演示”和“工具演示”使用固定脚本，不访问真实 LLM。公开的辅助文本可以显示，不读取或展示隐藏思维链。

解析 token 用量单独保存于 `semantic.analysis_usage`；任务执行用量保持在 `task.usage`。下载的任务报告包含两个阶段的来源、权限、内容证据和用量。

## 验证和当前边界

63 项自动测试全部通过，前后端类型检查与生产构建通过。新增的规则模式回归测试覆盖“解释报错，不要改代码”等请求，避免症状关键词覆盖解释/审查意图；它仍是基础规则整理，不等同于 LLM 理解。

Chrome 已验证需求执行预览、固定演示的完整交接与调用记录、任务丢弃、解释任务的 5 个只读工具范围，以及 390px 窄屏。未出现页面运行错误，窄屏页面没有横向溢出。

`tests/semantic.test.ts` 新增 7 项测试：

- 两种完整工作台协议：官方 SDK 连接本地模拟 API，完成 Structured Outputs → 创建任务 → Function Calling → 工具输出 → 最终结果。分别验证修复产生副本差异、解释只读及伪造写入被拒绝。
- 文件清单和空搜索不解除内容证据要求，连续无证据完成会停止。
- 同轮伪造写入被拦截，收到内容反馈后的下一轮才开放修改。
- 空工作区可以开始新增任务。
- 显式任务选项和语义解析都不能放宽项目只读配置，关键澄清未完成时禁止交接。
- 拒绝响应与函数调用混合时，没有工具副作用。

上述是离线协议与程序行为验证。当前机器未配置真实 API Key，也没有 Docker，尚未测量真实模型的语义准确率、工具决策成功率和容器检查效果。实际联调时，可分别尝试“解释空列表为什么报错”和“让空列表金额为零”，检查模型是否获取相关代码、是否遵守只读权限、修改是否通过独立测试。

CLI `run` 保持直接工具循环，不强制经过需求解析器。已有任务不自动补写语义上下文，不支持重启续跑。

- `src/analysis.ts`：Structured Outputs、澄清、版本化解析及交接。
