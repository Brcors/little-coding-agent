# Coding Agent 技术方案与完整构建过程

版本：方案 v1 · 2026-11-01

本文是最初的工程设计，阶段、接口、限制值和质量目标均为建议，不代表当前版本已实现全部规划。v0.5 的实际能力与验证边界见 [语义与工具调用实现](semantic-function-calling.md)。API 与基础工具事实在方案编写时对照官方文档核对，实际依赖以锁文件为准。

## 1. 产品目标与首版范围

构建一个本地运行的编程助手：用户选择代码仓库并描述任务，Agent 自主查找相关文件、提出并执行修改、运行检查，最后给出可审阅的代码差异和验证证据。

首版假设：Windows、本地单用户、云端模型推理、单 Agent、单任务串行写入。先交付 CLI，再提供浏览器中的本地工作台。工具层可以操作不同语言的源码；首批自动验收仓库以 TypeScript / Node.js 为主，Python 等语言的检查配置随后扩展。

首版能力：

- 选择仓库，发起新任务，继续会话，取消任务。
- 按文件名和文本检索代码，按行读取文件。
- 在独立任务工作区中创建、修改、删除文本文件。
- 执行配置好的测试、类型检查和构建，读取实时日志。
- 查看修改前后差异，接受或丢弃本次修改。
- 记录工具调用、检查结果、用量和任务状态，支持重启恢复。

模型通过 API 使用；构建重点是运行时、工具、上下文和交付流程。后续版本再增加 IDE 插件、MCP、符号检索、远程执行、团队协作和多 Agent。

首个演示任务：“修复一个边界条件错误，并补齐能复现它的测试。”完成证据是实际文件差异、检查命令、退出码和日志引用。

## 2. 总体架构

~~~text
CLI / 本地 Web 工作台
          │ 创建任务、取消、审阅
          ▼
本地应用服务 ───────── 事件流 / SQLite / 日志与差异文件
          │
          ▼
Agent 运行时（状态机、预算、取消、恢复）
          ├── 上下文管理 ── 仓库摘要、搜索结果、近期变更
          ├── 模型适配器 ── 云端模型 API
          │                    │ 结构化工具请求
          ▼                    ▼
工具路由 → 参数校验 → 权限与路径校验 → 执行器
          ├── 文件工具：任务工作区
          ├── Git 工具：基线、差异、接受修改
          └── 命令工具：受限容器 → stdout / stderr / exit code
                    │
                    └── 结果反馈给模型，进入下一轮
~~~

模型决定下一步需要什么信息或动作；运行时决定是否允许、如何执行、何时停止。所有读写和命令均经过工具执行层。界面只提交意图与展示事件，密钥和进程执行留在本地服务中。

首版主动维护 Agent 循环，以便控制本地文件、进程和恢复逻辑。模型端优先使用 Responses API 的函数调用；官方定义的流程是声明工具、接收调用、由应用执行并回传结果。参见 [OpenAI Docs：Function calling](https://developers.openai.com/api/docs/guides/function-calling)。

## 3. 技术选型

- 工程语言：TypeScript。CLI、服务和前端共享事件与工具类型，减少协议不一致。
- 运行时：Node.js 24 LTS，开发、CI 与发布验证使用同一主版本；补丁版本随实施锁定。该版本目前仍处于 LTS，见 [Node.js 发布状态](https://nodejs.org/en/about/previous-releases)。
- 依赖组织：npm workspaces，提交锁文件，CI 使用 npm ci。
- 模型接入：官方 openai SDK + Responses API。模型 ID 用配置项指定，启动时验证账户可用性和工具调用能力，不在业务逻辑中硬编码型号。
- 本地服务：Fastify，HTTP 命令接口 + SSE 事件流；用自有 JSON Schema 验证接口和工具参数。参见 [Fastify 校验文档](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)。
- 工作台：React + Vite，提供会话、工具记录、日志与差异审阅。Vite 提供 React / TypeScript 模板，见 [Vite 指南](https://vite.dev/guide/)。
- 持久化：SQLite，通过 better-sqlite3 适配；结构化记录入库，较大日志与文件快照放应用数据目录。原生模块在 Windows 安装与打包阶段单独验证，见 [better-sqlite3 项目说明](https://github.com/WiseLibs/better-sqlite3)。
- 仓库工具：Git + ripgrep。优先使用目录、文件名和文本搜索定位相关代码。
- 执行环境：Docker Desktop / Linux 容器；工作负载按语言配置镜像。Windows 专属构建命令后续由专用执行器支持。
- 验证工具：Vitest 做工具和状态机测试，Playwright 做工作台流程验证。参见 [Vitest](https://vitest.dev/guide/) 与 [Playwright](https://playwright.dev/docs/intro)。

这些选型是本方案的工程判断。首版按本地产品发布，无需引入公网部署、共享数据库或任务集群。

## 4. 工程目录与依赖方向

~~~text
coding-agent/
  apps/
    cli/                 命令行入口、配置、任务交互
    server/              本地 HTTP / SSE 服务
    web/                 会话、日志、差异审阅
  packages/
    protocol/            工具、事件、错误、状态的协议
    core/                Agent 状态机、预算、取消
    model-provider/      Responses API 适配与流式事件转换
    context/             相关文件选择、摘要、裁剪
    tools/               文件、搜索、补丁、命令、差异工具
    workspace/           仓库基线、任务工作区、接受与撤销
    executor/            容器执行与进程生命周期
    storage/             SQLite、迁移、事件日志
  tests/
    fixtures/            小型仓库与异常场景
    integration/         工具与执行器集成验证
    e2e/                 CLI / 工作台流程
    evals/               固定任务与独立验收器
  docs/
  package.json
  package-lock.json
~~~

protocol 不依赖界面或 SDK；core 依赖 provider、storage、tools 的接口；CLI、服务调用同一个 core。前端只能通过服务协议访问数据，不能直接拿到模型密钥。

## 5. 从零构建的十个阶段

### 阶段 0：确定任务与验收样本（1–2 工作日）

准备代码解释、修复错误、增加小功能、补测试、局部重构五类任务。挑选 20 个规模可控的样本，固定初始提交、任务描述和独立检查方式。

同时确定配置项、数据目录、任务终态和命令执行模式。产出需求说明、验收任务集、基本交互草图。通过条件：每个任务都有可观察的完成条件。

### 阶段 1：初始化工程与协议（1–2 工作日）

建立 workspaces、TypeScript 严格检查、格式和 lint 配置。创建 CLI、服务健康检查、存储迁移，以及工具请求和任务事件的共享类型。提供固定输出的假模型，开发时先验证流程。

拟定顶层脚本：dev、typecheck、lint、test、test:integration、test:e2e、eval、build。首次开发锁定依赖；构建代理自身不需要容器执行不受信仓库代码。

产出可启动的工程骨架。通过条件：干净安装后 CLI 能创建任务，服务能返回健康状态，事件能够写入并重放。

### 阶段 2：构建只读代码工具（2–3 工作日）

实现 list_files、read_file、search_text。统一相对路径、行号、分页、文件大小上限和结构化错误。默认排除依赖目录、二进制、Git 内部文件及敏感配置。

忽略规则既作用于搜索，也作用于直接读取；传给模型之前还要检查输出内容。Windows 测试覆盖中文、空格、盘符、路径大小写、CRLF、junction 与符号链接。

产出可查询代码库的 CLI。通过条件：能定位目标函数，同时拒绝跨目录与敏感文件读取。

### 阶段 3：实现任务工作区和可撤销补丁（2–3 工作日）

检查原仓库基线，在独立任务 worktree 中开展修改。Git 支持多个工作树，但共享仓库元数据，因此 worktree 用于组织代码修改；见 [Git worktree 文档](https://git-scm.com/docs/git-worktree)。

仓库存在未提交内容时，界面让用户选择以提交版本开始，或把选定的当前修改带入任务快照；不能静默忽略它们。尚无首次提交的仓库使用文件快照模式。

apply_patch 接收预期内容哈希与补丁；应用前检查所有文件前置条件，使用临时文件和变更清单，失败时恢复本批次。差异必须包含新增、删除和未跟踪文件。接受修改时再次验证原目录内容，冲突则进入审阅流程。

产出可查看、接受、丢弃的变更集。通过条件：失败和撤销只影响 Agent 的本次修改，不覆盖用户随后进行的编辑。

### 阶段 4：实现命令执行器（3–4 工作日）

为测试与构建准备容器执行器。只把经过筛选的任务源码副本送入容器；排除 Git 元数据、凭据和私有配置。模型调用留在宿主服务，密钥不注入测试容器。

默认使用非 root 用户、受限 CPU / 内存、只读基础文件系统及明确的可写目录；运行检查时关闭网络。依赖安装单独走受控准备步骤，固定锁文件和镜像，安装脚本同样在容器中执行。依赖缓存按锁文件隔离，避免任务间污染。

run_command 使用程序与参数数组，返回 command_id；poll_command 取增量日志，cancel_command 停止该任务容器。超时、取消与退出状态分别记录。Windows 主机模式如后续启用，需要处理 .cmd 启动及进程树清理，见 [Node 子进程文档](https://nodejs.org/api/child_process.html)。

产出能运行测试并留下证据的执行器。通过条件：成功、失败、超时、取消都可识别，任务结束后没有遗留执行进程。缺少 Docker 时仍能读码与生成修改，执行检查显示不可用。

Docker 默认没有自动配置的 CPU / 内存上限，需要显式设置，见 [Docker 资源限制](https://docs.docker.com/engine/containers/resource_constraints/)。隔离效果还取决于宿主与容器配置，见 [Docker 安全文档](https://docs.docker.com/engine/security/)。

### 阶段 5：接通模型并完成 Agent 循环（2–3 工作日）

实现 model-provider，把 SDK 输出转成统一事件；接收完整工具参数后再执行。模型适配器保存可续接的完整响应项，并将工具结果与 call_id 配对。工具只允许调用注册表内的函数。

先以假模型验证状态转移，再接真实模型处理单个小任务。每次模型请求都提供当前约束；设置轮数、时长、token 与工具执行限制。检查失败时反馈实际日志并允许有限修复，达到预算后明确结束。

产出可自主修复一个真实问题的 CLI。通过条件：整个“定位 → 修改 → 检查 → 修正 → 审阅”闭环无需开发者手工填充工具结果。

### 阶段 6：上下文、持久化和恢复（2–3 工作日）

上下文按“目标与约束 → 仓库摘要 → 当前相关代码 → 近期差异 → 最新检查结果”组织。先用搜索和按行读取控制体积，旧日志保留引用，摘要附原始文件与行号。更新文件后使旧片段失效。

SQLite 保存任务、响应项、工具调用、命令状态、事件、检查点及用量。中断后先核对进程和文件状态；对执行结果未知的写入不自动重放。

产出能够重启继续的 Agent。通过条件：断网、限流和进程崩溃不会导致补丁重复应用；模型停止与最终交付状态能正确区分。

### 阶段 7：构建本地工作台（3–4 工作日）

接入创建任务、取消、继续、授权、查看事件、查看差异、接受修改等接口。布局分为任务与文件导航、会话与工具记录、差异与检查证据。

使用 HTTP 提交操作，SSE 推送有序事件；通过事件序号支持断线续读。刷新页面只重放事件，不重放工具。等待授权时展示具体路径、命令及作用范围，已有授权范围内的动作继续执行。

产出可操作的浏览器界面。通过条件：用户能看清当前阶段、改了什么、检查结果、为何停止，并完成接受或丢弃操作。

### 阶段 8：执行系统测试与任务评测（3–5 工作日）

工具测试覆盖路径边界、补丁冲突、输出截断；集成测试覆盖真实临时仓库、容器超时、取消和崩溃；界面测试覆盖断线续读、授权及差异审阅。

固定 20 个任务做真实模型评测：按独立检查结果判定完成率，记录重复运行的波动、耗时、用量、无关修改和人工介入。验收器放在 Agent 可写区域之外，防止被任务修改影响。

产出评测报告与缺陷清单。通过条件见第 12 节；失败应能定位到模型决策、上下文、工具或执行环境。

### 阶段 9：打包、安装与发布（2–3 工作日）

按固定顺序执行安装、静态检查、测试、前端构建和 CLI / 服务构建。将前端产物随本地服务分发，定义 agent run、agent ui、agent doctor 三类入口，打包为 npm 安装包供首批用户使用。

在干净 Windows 环境安装产物，检查 Node、Git、ripgrep、Docker 和 SQLite 原生依赖，跑一次真实修复任务。CI 分别验证 Windows 与 Linux；只承诺通过安装和执行验证的平台。

产出版本化安装包、使用说明、数据库迁移与回退说明。通过条件：新机器可完成安装、配置模型、创建任务、审阅修改及取消执行。

上述工期合计约 21–32 个工作日，属于一名熟悉 TypeScript 与 Agent 工程的开发者全职工作的规划估计，约 4–7 周；不含远程多租户平台与额外语言执行器。

## 6. Agent 循环与结束条件

~~~text
创建任务并固定基线
  → 选择上下文与注册工具
  → 请求模型
  → 持久化完整响应项
  → 存在工具调用？
      是：校验 → 授权检查 → 执行 → 记录结果 → 反馈模型 → 下一轮
      否：检查候选交付物与验证证据
  → 未通过检查：在预算内继续修复
  → 已通过：生成差异与报告 → 等待审阅
  → 用户接受修改：完成
~~~

建议状态：

queued → preparing → generating → executing / waiting_approval → verifying → review_ready → completed。

任一活动状态可转 cancelled、failed、budget_exhausted 或 needs_input。网络超时、API 拒绝、环境缺失、测试失败使用不同错误原因。存在工具调用或待执行检查时，普通文字回复不能直接结束任务。

初始建议值：最多 30 次模型请求、任务 15 分钟、单条检查命令 120 秒；均可配置。超出限制后保存差异和证据，说明尚未完成的部分。重试同样计入预算。这些值是产品默认值建议，不是服务商限制。

实现时使用官方 SDK 当前支持的响应项续接方式，保留完整 output 中需要的项目；不要仅保存可见文本。参见 [OpenAI Docs：会话状态](https://developers.openai.com/api/docs/guides/conversation-state)。不展示模型隐藏推理，界面展示简短计划、工具事件与可验证结果。

## 7. 工具协议

首版工具注册表：

- list_files：相对目录、过滤条件、分页 → 文件路径及类型。
- read_file：相对路径、起止行 → 带行号内容、当前哈希、截断标记。
- search_text：模式、相对范围、匹配上限 → 路径、行号和片段。
- apply_patch：各文件预期哈希、变更内容 → 新哈希、受影响路径和变更集 ID。
- run_command：配置中的程序、参数数组、相对 cwd、时限 → command_id 与初始状态。
- poll_command：command_id、日志游标 → 新日志、状态、退出码。
- cancel_command：command_id → 该任务执行器的终止结果。
- inspect_diff：任务 ID → 基线到当前的文本差异、文件状态和制品引用。

接受修改是用户应用操作，不向模型开放。工具请求还携带由运行时绑定的 task_id、workspace_id 和 call_id；模型参数不能切换任务工作区。

统一返回 ok、data、error_code、retryable、truncated、artifact_ref。错误码至少区分 PATH_DENIED、STALE_CONTENT、PATCH_CONFLICT、TIMEOUT、CANCELLED、ENV_UNAVAILABLE。

工具声明使用严格 JSON Schema，服务端仍检查实际参数与权限。读工具可分页；建议单次回传文本控制在约 40 KB，完整脱敏日志存本地，通过游标补读。文件写入按任务串行，独立读取之后再按测量结果考虑并行。

## 8. 权限、路径与执行边界

权限是运行时配置。用户选择任务范围后，可以让读取和任务工作区内的可撤销修改持续执行；对安装依赖、开放网络、主机命令和外部写入分别定义授权范围。首版不提供发布、推送或发送消息类工具。

文件访问按真实路径判定，处理 ..、绝对路径、UNC、盘符和路径分隔符；现有路径解析 symlink / junction，新文件校验已存在的父目录。避免以简单字符串前缀判断路径归属。阻止修改 Git 元数据、执行器配置和本机凭据。

仓库里的说明、代码注释、工具输出均作为待处理数据；它们不能改变顶层权限。秘密文件忽略规则必须覆盖读取、搜索、容器输入和模型出站内容，日志也要脱敏。

文件路径规则无法限制任意子进程的系统调用。因此默认命令进入受限容器；容器只接收该任务需要的文件，不挂载宿主 HOME、SSH、Docker socket 或 Git 凭据。容器内部生成的文件也不会整体复制回宿主。

本地服务只绑定 loopback，使用启动会话凭据，校验 Origin / Host 并限制写操作请求。浏览器存储与前端构建产物中不放模型 API Key。密钥由本地服务从受限配置或凭据存储读取。

## 9. 状态与数据模型

最小数据实体：

- projects：仓库真实路径、配置与信任状态。
- sessions / tasks：会话、目标、状态、基线、预算、模型与策略版本。
- model_turns：响应 ID、可续接的响应项、状态和用量。
- tool_calls：call_id、经校验的参数、状态、脱敏结果引用。
- commands：执行器 ID、启动与结束时间、退出码、日志游标。
- events：task_id、单调序号、类型、时间、载荷。
- checkpoints / artifacts：文件哈希、恢复信息、差异、测试日志和报告。
- approvals：具体授权范围、有效期、决定。

事件与状态更新使用数据库事务。大文本按引用读取，设置留存与总量限制。数据库默认位于用户本机应用数据目录，任务 worktree 和数据库建议放在非同步目录，减少 OneDrive 文件锁与同步竞争；原始项目仍可位于同步目录。

恢复语义采用“可检测并补偿”，不承诺跨数据库与操作系统副作用的绝对恰好一次。执行前记录意图，执行后记录证据；恢复时核对内容哈希与执行器状态，结果未知的动作进入核查状态。

## 10. 服务接口与事件

建议接口：

~~~text
POST /tasks                     创建任务，支持客户端幂等键
GET  /tasks/:id                  任务状态与摘要
GET  /tasks/:id/events           SSE；按事件 ID 续读
POST /tasks/:id/cancel           取消任务与关联执行器
POST /tasks/:id/resume           从已核对的检查点继续
POST /tasks/:id/approvals        对具体授权请求作出决定
GET  /tasks/:id/diff             完整变更集，含新增文件
POST /tasks/:id/accept           验证原目录基线后应用修改
POST /tasks/:id/discard          丢弃任务变更
GET  /artifacts/:id              读取经授权的日志或报告
~~~

事件包括 task.started、model.text.delta、tool.requested、approval.required、tool.completed、command.output、verification.completed、task.review_ready 和 task.finished。

幂等键防止用户重复点击创建任务；数据库 call_id 唯一性防止重放同一工具调用。事件补发只改变展示，不重新执行动作。取消要同时停止后续模型请求和已运行的命令。

## 11. Prompt 与上下文策略

系统约束说明可使用的工作区、工具、预算、交付证据及敏感信息规则。任务指令表达目标、验收标准和范围。项目约定经筛选后加载，仍受产品执行策略约束。

模型应先查询相关代码，修改后检查实际差异，按项目配置运行验证，并基于结果报告。无法运行的检查标记为“未验证”，不能写为“通过”。用户改变任务范围时，更新目标与验收标准并记录版本。

长任务保留目标、授权、已变更路径、最新检查失败和下一步；旧证据保存为引用。压缩只处理已闭合的历史片段，不能拆开尚未匹配完成的工具调用与结果。搜索片段按文件哈希失效，避免根据过时代码继续修改。

## 12. 测试与验收标准

确定性工程测试：

- 所有路径边界、越权读写、敏感文件与未授权执行样本必须通过。
- 补丁冲突、用户并发编辑、取消、命令超时和崩溃恢复不丢失原始改动。
- 工具调用与结果可对应；未知副作用不会在恢复时自动重放。
- SSE 重连和界面刷新不会重复触发命令。
- 修改验收仅基于实际差异与检查结果，未运行的测试显示未验证。

真实模型评测：

- 首批 20 个固定小任务，初始目标为独立验收完成率至少 80%；这是目标，尚无实测结果。
- 每个任务重复执行并记录波动；区分模型能力失败与环境失败。
- 记录每任务请求数、输入输出用量、检查轮数、总时长、无关修改和人工介入。
- 固定模型 ID、参数、Prompt、工具版本及仓库基线，使版本之间可比较。
- 评测时使用 Agent 不可修改的验收器；同时检查原功能回归。

上线前至少用干净环境走通：安装 → doctor → 配置模型 → 修复样本 → 检查 → 审阅 → 接受修改，以及中途取消和恢复两条异常路径。

## 14. 成本、风险与演进

每次模型响应记录服务商返回的 token 用量。费用按“未命中缓存的输入用量 × 输入单价 + 缓存输入用量 × 缓存单价 + 输出用量 × 输出单价”累计估算，避免重复计算缓存部分；单价按模型和日期配置，不在此写死。预算检查要为下一次请求预留输出上限，停止后仍核对在途请求实际用量。

主要工程风险及处理：

- 上下文偏离：相关文件检索、按行读取、哈希失效、失败任务回放。
- 补丁破坏已有编辑：基线与预期哈希、独立工作区、接受时冲突检查。
- 命令失控：独立执行器、资源限制、超时及完整生命周期管理。
- 模型过早声称完成：状态机约束与独立验证证据。
- API 中断或重复请求：持久化响应与工具 ID，按副作用类型恢复。
- Windows 差异：中文路径、CRLF、原生模块、.cmd、进程取消专项验证。
- 开发范围膨胀：按十个阶段交付，CLI 闭环可用后再推进工作台与扩展。

后续顺序：先根据真实任务失败数据优化检索、Prompt 和工具，再增加符号索引与语言执行器；需要外部能力时接 MCP，需要复杂任务分工时再评估多 Agent。每次升级模型或工具后重跑固定评测。
